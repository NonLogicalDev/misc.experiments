# Construction-based topology queries: design and tests

## Recommendation

Build the query system around a typed graph of model operations and B-rep entities. Queries should use construction history and topology relationships directly, with geometry available when the intended distinction is spatial. Do not require every shape to have named sides, a start or end, a preferred axis, or a particular primitive type. A reference to an input entity may itself come from an earlier query or a deliberate inspection selection; a domain-specific name is optional.

Keep the full, operation-local history graph. An entity reference includes its model scope, producing operation, output body and entity, not a bare index. History edges retain their operation, operand position, source and result. Preserve distinct events for retention, modification, splitting, merging and generation, including a face generated from an edge and an edge created where two faces meet. A kernel must distinguish a reported complete history, a known root and unavailable history; an absent report is not evidence that an entity was deleted.

An operation-local reference identifies an entity in one evaluation. It does not by itself identify the same authored source after a rebuild. A durable selection needs an authored entity reference, a query evaluated again at the source stage, or an explicit repair workflow; copying a stage-local index or hashing a record does not supply that contract. Profile-segment ordinals in the current history schema are scoped to the producing operation and need a separate mapping to persistent sketch entities.

Source capture must be specified, not hidden in an unexplained variable. The [adapter source-capture example](selection-library.md#where-the-source-reference-comes-from) shows how the existing named-box `face_ref` API produces an actual source reference, and what needs to change in the adapter to retain it. The [test](../artifacts/test-source-capture.py) checks that reference and its reported descendants against both adapter sides. This covers a named box, not arbitrary operations: stable authored sketch entities, generated-face references, automatic source-query suggestions and recovery from ambiguous or missing history remain design work.

The richer [`solidcore-record` history](../../../../vendor/solidcraft/solidcore/crates/solidcore-record/src/brep/history.rs) already models face changes, generated faces from input edges or profile segments, and edges from input edges or meetings between face origins. The [SolidCraft kernel wrapper](../../../../vendor/solidcraft/crates/kernel/src/boolean_record.rs) composes operation-local histories when possible. This is useful prior art inside the dependency; it is not yet the production SolidRecipe query engine. Its `History::substitute` explicitly refuses some compositions, including a blend of an edge generated by the preceding operation. An experimental probe of an existing prebuilt SolidCraft library reproduced that refusal for a real cut followed by a fillet; because that library predates some vendored working-tree changes, the probe does not establish the behavior of the current source build.

The [same probe](../artifacts/probe-rich-history.rs) checked a sphere cutting a box corner: the prebuilt kernel reported one spherical result face and three edges where that face meets three distinct box-source faces. The recorded edge-face uses agreed with the resulting B-rep. This is evidence for a curved case on that build, not a guarantee for other surfaces or current source revisions.

## Operators and contracts

Separate a small semantic core from convenient syntax. The proposed core is:

1. **Entity scope:** enumerate typed bodies, faces, edges, vertices and, where supported, uses and loops in one evaluated body or explicitly named collection of bodies. A query declares its evaluation stage; it cannot refer to the output of the operation it is selecting inputs for.
2. **History relationships:** ask whether an entity is a descendant of an earlier entity, was created or modified by an operation, or was made from specific inputs. Keep these relationships distinct: a face generated by filleting an edge is not merely a face descendant of that edge; an edge between two faces is not necessarily newly generated by the latest Boolean. Allow a query to retain both sides of a recorded meeting and to follow paths through multiple operations.
3. **Topology relationships:** relate entities through actual incidence, including edge uses and face uses. A generic pattern can bind several entities and require distinct witnesses. For a manifold body, a convenience operation for edges between two face sets requires two distinct incident faces, not merely two membership tests that the same merged face can satisfy. Non-manifold bodies need an explicit co-incidence or radial-neighbor definition; face IDs alone do not establish a particular opposite side.
4. **Composition:** combine conditions with conjunction, disjunction, negation and bound variables; form sets by union, intersection, difference and projection. This provides correlations between witnesses without adding an application-specific method for every feature. A connected-component or traversal operator extends the core for arbitrary-length chains.
5. **Checks and geometry:** require a complete result and, when appropriate, an expected count or one result. Geometry, orientation, units, whole-entity versus intersection semantics and tolerances are explicit relationships where needed, not a replacement for available construction history.

These are semantic operations, not a settled public method list. `edges_of`, `vertices_of` and `edges_between` can be readable conveniences. A query is a rule that can be reevaluated; an identity reference instead asks for the same intended entity. Both must surface ambiguity. If a source edge splits, a query for all descendants can intentionally return both; a strict single-edge reference should report the split and require a policy or repair. Never pick a result by record order as an implicit tie-breaker.

## Tests on actual constructed geometry

All examples use the current project debug executable unless stated otherwise. The Python scripts create graphs in memory, write no model outputs, and use an independent geometric or topology oracle to check results. The proposed query engine itself is not implemented; these are executable experiments on reported history and actual B-rep adjacency.

- [Adapter experiment](../artifacts/test-construction-queries.py): the source-face and edge-incidence formulas reproduced both user-selected sets for the original left 4.6 mm parameters. The same underlying relations matched geometric oracles on left heights 4.5, 4.6 and 4.7 mm and right heights 4.5 and 4.7 mm, at the applicable stages. It also matched the two entry edges, the setback edge and all four hole rims in those configurations. The report has untracked blend faces, so these matches are not a completeness certificate.
- [Actual vertex probe](../artifacts/verify-adapter-vertices.py): independent B-rep rebuilds have a single topological vertex at the selected corner with three incident edges for each of those five configurations. On the left 4.6 mm rebuild those are indices `35`, `36`, `43`; the original selection came from a different preview snapshot. The probe links an existing Rust library and explicitly does not prove source/build freshness by itself.
- [Other shapes](../artifacts/test-query-shapes.py): the interface expression selected and geometrically checked rims of cylindrical through and blind holes, a square through-hole, shifted and resized stock, and two separately named holes. It excluded the same-face seam on the cylindrical cases. It also selected the four source-face interface edges in separate box cut, union and intersection examples, checked against their known geometry. A rectangular Boolean's four upper intersection edges were selected, passed by their measured midpoints to the existing point-based fillet API, and filleted; the four lower edges remained. That last test does **not** implement a direct query-to-fillet handoff.
- [Model edits](../artifacts/test-query-metamorphic.py): source-based selections for two holes matched geometric checks after changing cut order, moving holes, changing radius, exchanging the holes' positions and translating the result. Swapping operation order changed snapshot indices. A larger later hole left no reported descendants of the earlier hole wall; the current report cannot distinguish deletion from lost history.
- [Later cut on adapter](../artifacts/test-query-perturbations.py): after adding a bore through the slot wall, the earlier “all wall boundary except its floor” expression returned six edges, including two new bore edges. The positive expression using the previously identified three source-side relationships returned four edges: the former upper edge split into two. Which behavior the user wants is an intent question; this example shows that the two expressions are not interchangeable.
- [Candidate miner](../artifacts/mine-selection-candidates.py): without hand-picking a face name, the experiment finds a common-face and neighboring-source-face explanation for edges `6`, `9`, `16` on the named, rebuilt adapter. It refuses faces with ambiguous or unavailable reported origins. That pattern class does not explain `35`, `36`, `43`; a shared-vertex pattern is a separate candidate. The result illustrates how the viewer could suggest construction-based queries, not infer the user's intent uniquely.
- [Merge and split counterexamples](../artifacts/test-query-shapes.py): a notch splits one named source edge into two descendants. Two adjacent boxes merge their coplanar top faces; the single merged face carries both source identities and a query for a face with the first source can reach an edge outside the first box's original extent. Entity-level contribution is not a map of the source's local region. Another notch makes the union of pairwise face interfaces select four edges although only three touch the intended corner; use a correlated shared-vertex condition when that is the intended rule.

The identified slot-side and corner descriptions are hypotheses about the user's intent. Matching a recorded set does not prove that the author intends the same response to every possible edit. Count checks can catch some changes but cannot prove intent or the absence of a wrong match.

## What generalizes, and what cannot be proved from these tests

For finite, complete typed entity and relationship tables, relational algebra with product/join, filtering, projection, union and difference expresses the domain-independent first-order queries over the supplied relations. The argument is by structural translation between those operators and bound-variable formulas. This is a statement about expressibility given the facts, not a proof that the kernel supplies those facts or that all CAD intentions are first-order. Reachability needs a traversal or transitive-closure extension. See [Codd's relational completeness](https://db.dobo.sk/wp-content/uploads/2015/11/Codd_1972_Relational_Completeness.pdf) and [finite model theory](https://www.cs.toronto.edu/~libkin/fmt/fmt.pdf).

[test-relational-queries.py](../artifacts/test-relational-queries.py) exhaustively checked all 4,096 two-edge/three-face incidence graphs and source memberships against an independently written interface computation, including 49,152 edge/face renumberings. Intersecting separate adjacency results gave a false positive in 1,011 of these cases. It also checked 4,096 three-node reachability cases and 24,576 renumberings. These finite checks support the formulas; they are not a proof about every B-rep or kernel operation.

An automorphism of the available facts that exchanges two entities also exchanges the result of any query defined solely from those facts. If the structure and all supplied labels remain unchanged by the swap, an invariant query cannot select exactly one of the two. To distinguish symmetric entities, the author must provide a distinguishing source reference, feature instance, spatial datum or other fact. An arbitrary index is not evidence of intent. Research on [generic naming](https://www.cs.purdue.edu/cgvlab/www/resources/papers/Capoyleas-Computer_aided_design-1996-Generic_naming_in_generative.pdf) discusses analogous structural ambiguities.

## Incomplete history and results

An experimental evaluator can represent a result as a set of **certain** matches and a set of **possible** matches. For selections `A = [A_low, A_high]` and `B = [B_low, B_high]`, difference has conservative bounds `[A_low − B_high, A_high − B_low]`; union and intersection combine corresponding bounds. Positive incidence can be evaluated on lower and upper sets. These formulas assume a complete, known entity universe and sound input bounds. An unknown body or incomplete enumeration needs a separate completeness flag.

[test-query-bounds.py](../artifacts/test-query-bounds.py) checked 2,187 small set-operation cases and 1,296 uncertain incidence cases against concrete completions. The bounds are tight for independently varying membership inputs in those tested cases. They may be imprecise when facts are correlated: treating the same unknown set as two independent inputs makes `A - A` appear possibly nonempty even though it is empty. Conservative uncertainty is preferable to inventing certainty; an implementation may retain correlations to improve precision.

In one adapter snapshot, treating reported untracked faces as potentially belonging to either source yields three certain slot edges and seventeen possible edges under a conservative interval calculation. Those are diagnostic bounds conditional on the report's flags, not production guarantees: the present report does not certify complete provenance.

## Edge portions and operations

An edge query selects existing topological edges. Selecting only part of an edge requires either an operation that accepts a parameter interval or a separate topology split. The latter must keep both incident faces, trim their parameter-space curves, introduce a vertex and report ordered child intervals. A parameter fraction is not generally an arc-length fraction; closed curves need an explicit anchor and direction. The bundled [record splitter](../../../../vendor/solidcraft/crates/geom/src/brep/split.rs) demonstrates some of these representation requirements, but SolidRecipe does not expose it as an edge-split and the ability to fillet just one resulting child has not been established.

## External reference points

- [A Lineage-Based Referencing DSL for Computer-Aided Design](https://doi.org/10.1145/3591223) (Cascaval, Bodik and Schulz, 2023; [open paper](https://par.nsf.gov/servlets/purl/10461767)) defines `from`, `derivedFrom`, `contains`, Boolean composition and all/any combinations over an operation lineage graph. It distinguishes subset, transform and deriving relationships, and proves selectability under its language and operation assumptions. Its implementation uses a 2.5D kernel, assumes statically accessible primitive elements, and excludes fully general spline intersections from the selectability guarantee. The paper explicitly leaves synthesizing lineage queries from graphical selections as future work. This is much closer prior art than the generic relational-algebra baseline; compare its definitions and limitations before selecting SolidRecipe's query semantics.
- [BRepQL](https://doi.org/10.1016/j.compind.2024.104207) (Lim et al., 2025; [abstract](https://pure.korea.ac.kr/en/publications/brepql-query-language-for-searching-topological-elements-in-b-rep/)) proposes a language for searching B-rep topology and composing queries into procedures. The abstract reports successful searches and tests on modified models where the specified topology and geometry constraints were preserved. Only the abstract was reviewed here; its operator set, full evaluation and treatment of construction history remain unverified.
- [Onshape FeatureScript queries](https://cad.onshape.com/FsDoc/modeling.html) distinguish a query description from the entities found when evaluating it. Its [standard library](https://cad.onshape.com/FsDoc/library.html) provides operation-created entities, adjacency, set operations and tracking. Its documented tracking distinctions between derivation and identity are useful; they are not evidence that SolidRecipe already implements them.
- [Open CASCADE history](https://dev.opencascade.org/sites/default/files/documents/release_notes_7.2.0.pdf) records generated, modified and removed entities and composes operation histories. Capability and completeness remain operation-specific.
- [Interactive Programming for Parametric CAD](https://dzufferey.github.io/files/2020_Interactive_Programming_for_Parametric_CAD.pdf) explores synthesizing selections from examples. Multiple descriptions can fit the same example, so inferred intent should remain visible and testable.
- [Persistent naming through persistent entities](https://graphics.tudelft.nl/Publications-new/2002/BB02a/BB02a.pdf) examines references that survive changes in boundary topology. Rich construction history improves the available evidence; it does not guarantee a unique intended successor in every edit.

## Remaining work

- Connect the richer operation-local history graph to actual SolidRecipe evaluation and validate its coverage and missing-history behavior on each supported kernel operation.
- Expose same-record vertices, uses and faces to an experimental evaluator; preserve multiplicity and body scope. Evaluate the shared-vertex expression itself rather than using pairwise face interfaces as a proxy.
- Add an explicit query input to blends and test it against the same recorded B-rep; the current half-interface test uses the point picker as a bridge.
- Extend tests to sketch-driven extrusions, revolutions, curved/freeform surfaces, non-manifold topology, explicit split operations, imported bodies and more parameter changes as those inputs become available. An arbitrary imported body may have no construction history and must fall back to other stated evidence.
- Design source-reference capture and instance identity without implicit universal feature roles. Test feature deletion, suppression, reordered graph nodes, repeated instances and exact behavior at split/merge events.
