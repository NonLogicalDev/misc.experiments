# Selection and query library

This library records concrete selections and candidate ways to describe them. It is evidence for designing the [general query algebra](topology-query-algebra.md), not a list of implemented SolidRecipe APIs. A query below is **pseudocode** until an actual evaluator and its geometric predicates are implemented and tested.

The initial examples use the [NH-L12S adapter prototype](../../../../examples/cooler_adapter.py), an exploratory comparison model, not a verified manufacturing design. Indices and hashes identify records within one evaluated snapshot; they are not persistent references. A description of a set may intentionally select different entities after a rebuild. When facts cannot be established, selection must report uncertainty instead of silently discarding candidates.

## Construction-first operator proposal

The following is a design sketch, not executable Python. The model would retain references to selected source entities from its construction. Those entities can come from any feature or earlier selection; there is no universal `start`, `end`, `back`, `roof`, or `inner` face on an arbitrary shape. The variable names below describe this specific adapter, not properties required of a model. The author may name features or source entities when those names have meaning, but the operators must also work with source references obtained by a prior query or inspection.

`faces_from(body, source_faces)` means current faces with a recorded contribution from those source faces. It is not simply “faces generated by an operation”: it must account for preserved, modified, split, merged and deleted faces. Source-face references and that history are not available for all operations today. **A merged face can extend beyond its source:** entity-level lineage does not identify which portion came from which source. Do not treat a contribution as proof of local correspondence.

### Where the source reference comes from

The adapter currently constructs its base as an unnamed box and immediately assigns it to `shape`. To reference one of that box's faces, retain the box and give it an explicit feature ID. In this particular model the base is on the XY plane, so its face at minimum Z is the one intended for the setback query:

```python
import solidrecipe as sr

base = sr.Box(12.5, 71, 8.5).with_metadata(id="base")
base_face = base.face_ref("z_min")
```

`face_ref` is an existing API in the embedded runtime, and this returns `{"feature": "base", "kind": "face", "role": "z_min"}`. The feature ID and choice of face are real inputs; they are not inferred by the query. The box role is appropriate to this one construction, not a required vocabulary for arbitrary solids. In the adapter, `shape = base` would replace the present first `block(...)` call. For the matching left-side setback cutter, the actual source reference can likewise be captured:

```python
setback = sr.Box(1.1, 71.2, 7.5 - slot_height,
                 origin=(-0.1, -0.1, -0.1)).with_metadata(id="setback")
setback_face = setback.face_ref("x_max")
```

The adapter would use that `setback` as the operand of its existing subtraction. On the right side its mirrored cutter uses `x_min` for the corresponding face. The experiment [test-source-capture.py](../artifacts/test-source-capture.py) performs these actual `face_ref` calls, then checks their reported descendants and the common edge in the instrumented pre-chamfer adapter. It does not add IDs or change the original model file.

Given those two **defined** references, the proposed query is:

```text
# Proposed operations, not current SolidRecipe Python.
base_faces = faces_from(before_chamfer, base_face)
setback_faces = faces_from(before_chamfer, setback_face)
edge = expect_one(edges_between(base_faces, setback_faces))
```

The current `face_ref` method covers the limited named-primitive identities already implemented; `faces_from` and `edges_between` above are not implemented API. For an arbitrary construction, the equivalent source may be an authored sketch entity, a face generated by a prior operation, or the result of an earlier query. The history system must carry those actual entities and their origins; it cannot conjure a unique reference from an unlabelled shape. A viewer can trace a picked result back through history and propose a source-based query for review. The [candidate-mining experiment](../artifacts/mine-selection-candidates.py) demonstrates one narrow instance of that, not a complete automatic solution. If several source explanations fit, or the needed history is unavailable, the system must present that ambiguity rather than silently choosing.

`body` denotes the specified intermediate or final result in each example, not one shared body for all examples. `edges_of` and `vertices_of` return incident entities. For a manifold solid, `edges_between(A, B)` requires two distinct incident faces, one in each set; an edge used twice by one cylindrical face is not an interface with a different face. For non-manifold topology, co-occurrence of face uses does not by itself establish a particular opposite-side relationship; this proposed shortcut needs a more specific contract or must refuse that case. Sets support union, intersection and difference. `expect_one` and `expect_count` validate results instead of choosing arbitrarily. These are candidate user-facing conveniences over history, incidence, set operations and cardinality; names and exact signatures remain open.

The experimental harness [test-construction-queries.py](../artifacts/test-construction-queries.py) has evaluated the face-source and edge-incidence formulations for the two user snapshots and several intermediate stages; the results and limitations are recorded separately. Blends, merging and additional cuts may produce more faces or edges than the examples expect. A count check detects some changes but does not prove correct lineage or intent. When history is incomplete, the query must report it; geometric predicates and tolerances are explicit alternatives, not a silent substitute.

For the earlier Boolean example, the same interface operator can begin with faces descended from the two operands. Selecting only some of those intersection edges still requires a stated distinguishing relationship, such as adjacency to a named face or location relative to an authored datum; the operation history alone may not distinguish symmetric edges. To operate on part of an edge's length, selection is not enough: a separate split operation must create addressable segments, and the kernel must support the requested downstream operation on those segments. Neither behavior is proven here.

The following case descriptions retain measured geometry as independent evidence and describe the construction-based candidates. The names given to source faces are specific to these examples, not a prescribed vocabulary for arbitrary models.

## Three edges at the raised-strip corner

- **Intent:** Preserve the user's selection of the three edges meeting at the corner where the thin strip joins the raised section. The geometric descriptions below are hypotheses about the user's intended rule, not a claim that the user specified one.
- **Model and stage:** Final adapter, left side, slot height 4.6 mm, entry fillets and underside chamfer enabled; output `mounts.adapter`.
- **Observed selection:** Preview session `solidrecipe-preview-S1bnMv`, revision 1, edge indices `35`, `36`, and `43`. All three have an endpoint at `(3, 10.85, 8.5)` mm. The inspection-record hashes supplied with the selection were independently matched to these three records. See the [full adapter case](adapter-query-case.md) for hashes, face planes and measurements.
- **Candidate query:** Trace three previously identified source faces into the result, find their common vertex with three distinct face witnesses, then select its incident edges.
- **Expected and checked:** The selected snapshot had exactly the three observed endpoint matches. An endpoint scan of left and right snapshots at slot heights 4.5 and 4.7 mm, with both blends enabled, also found three matches in each. On the selected snapshot only, a separate face-plane/adjacency scan returned the same three edges.
- **Limits:** Endpoint coincidence is not proof that the ends share one B-rep vertex; the proposed incidence query was not executed. It would exclude an edge passing through the corner without ending there. Plane-based adjacency can also select distant or split edges. No check establishes the intended behavior under every edit.

```text
faces_a, faces_b, faces_c = faces_from(adapter, each_of_three_source_face_sets)
corner = vertices incident to distinct witnesses from faces_a, faces_b, faces_c
selected = edges_at(expect_one(corner))
```

## Three sides of the slot's back wall

- **Intent:** Record the user's second selection. One possible description is the back wall's boundary excluding its bottom edge; this description is a candidate, not an intent the user explicitly stated.
- **Model and stage:** Final adapter, left side, slot height 4.6 mm, entry fillets and underside chamfer enabled; output `mounts.adapter`.
- **Observed selection:** Preview session `solidrecipe-preview-S1bnMv`, revision 1, edges `16`, `9`, and `6`. All three user-supplied inspection-record SHA-256 values matched records retrieved from that session. Edge `16` runs from `(9, 8, 2.8)` to `(9, 8, 7.4)` mm; edge `9` runs from `(9, 8, 7.4)` to `(9, 54, 7.4)`; edge `6` runs from `(9, 54, 2.8)` to `(9, 54, 7.4)`.
- **Candidate query:** Trace the previously identified source faces for the back wall and the three neighboring sides into the result; select the edges between them. The labels describe this adapter, not universal model properties.
- **Expected and checked:** A scan of the original snapshot found one planar face on `x=9`, face `5`. Its boundary contains edges `6`, `9`, `16`, and `18`; edge `18` is a straight line on `z=2.8`. The source-and-incidence experiment returned exactly `6`, `9`, and `16` on the rebuilt left 4.6 mm body, and matched independent geometric checks in all five tested side/height configurations.
- **Limits:** This is an independent inspection scan, not execution of the proposed query language. It uses global planes for the observed left-side case; a reusable query needs side-aware authored datums, a coordinate frame, a tolerance and a definition of whole-edge plane membership. Other geometry may introduce multiple back-plane faces, split boundaries or extra floor edges. The data does not prove persistent identity or the user's intent after an edit.

```text
back = faces_from(adapter, back_source)
neighbors = faces_from(adapter, neighboring_source_faces)
selected = edges_between(back, neighbors)
```

The construction-based version was tested against the original selection. A [later-cut experiment](../artifacts/test-query-perturbations.py) shows why the older alternative of selecting all back-wall boundaries except the floor expresses different intent: it includes new boundaries made by the later cut.

## Two vertical slot-entry edges

- **Intent:** Identify the two entrance edges selected for the adapter's existing 2 mm fillets.
- **Model and stage:** Before entry fillets, after the initial groove cut; side `left` or `right`, slot height 4.5 or 4.7 mm.
- **Observed snapshot examples:** Left edges `18`, `16` at `x=0`, `y=8` and `y=54`; right edges `25`, `23` at `x=12.5`, `y=8` and `y=54`. Each is vertical and runs between `z=7.4` and `z=7.4-slot_height`. These indices were observed in the four independent snapshots described in [inspection evidence](../artifacts/adapter-snapshot-evidence.md).
- **Candidate query:** Trace the previously identified stock face and the two cutter faces into the pre-fillet result, then select their common edges.
- **Expected and checked:** The source chooses two entry edges with points before the fillets. The experimental source-and-incidence computation matched those edges against independent endpoint checks in all five tested side/height configurations.
- **Limits:** A geometric predicate using only direction, inside plane and length equal to slot height accidentally includes a raised-spine edge at height 4.5 mm. The source-based experiment depends on named construction inputs and reported history; current inspection does not certify that all operation history is complete.

```text
selected = edges_between(faces_from(before_entry_fillets, stock_face_source),
                         faces_from(before_entry_fillets, two_cutter_face_sources))
```

## One of the two entry edges

- **Intent:** Select one edge from the pair above using an explicitly identified source face, to test set refinement; this is an example subset, not a recorded user selection.
- **Model and stage:** The same pre-fillet snapshots and parameters as the entry-edge pair.
- **Observed snapshot examples:** The listed entry edge at `y=8` is left `18` or right `25`; the one at `y=54` is left `16` or right `23` in the checked snapshots.
- **Candidate query:** Restrict the entry-edge set to edges incident to the chosen source face's descendants.
- **Expected and checked:** One of the two identified entry edges is at each of the two stated y coordinates. The complete candidate query and the absence of other matches have not been evaluated.
- **Limits:** The author must supply a meaningful way to identify one source face. Nothing about an arbitrary shape provides an inherent first end. A split or merge may make a once-unique result multiple or ambiguous.

```text
selected = entry_edges & edges_of(faces_from(before_entry_fillets, chosen_source_face))
```

## Full-length underside setback edge

- **Intent:** Describe the edge currently chosen for the 1 mm underside chamfer without a point selector.
- **Model and stage:** Before underside chamfer, after entry fillets, setback cut and both screw-hole cuts; either side, slot height 4.5 or 4.7 mm.
- **Observed snapshot examples:** Left edge `46` lies at `x=1`, `z=0`; right edge `47` lies at `x=11.5`, `z=0`. Each is straight and 71 mm long in the checked snapshots. The model currently chooses it using a point at `y=35.5`.
- **Candidate query:** Trace the previously identified source faces of the bottom and the setback into the result, then select their common edge.
- **Expected and checked:** The experimental source-and-incidence computation matched the full-length edge against an independent endpoint check in all five tested side/height configurations. Uniqueness is not established for arbitrary edits.
- **Limits:** A future cut could split the edge into several collinear fragments; the query then describes a set and a uniqueness assertion must fail rather than choose one. The setback generates this edge; current lineage does not give it a proven persistent identity.

```text
selected = edges_between(faces_from(before_underside_chamfer, bottom_source_face),
                         faces_from(before_underside_chamfer, setback_source_face))
```

## Four screw-hole rims

- **Intent:** Select both the top and bottom rims of both screw holes; this is a modeling exercise, not a recorded user selection.
- **Model and stage:** Before underside chamfer, with entry fillets enabled, after both screw-hole cuts; either side, slot height 4.5 or 4.7 mm.
- **Observed snapshot examples:** Left edges `30`, `45`, `49`, `50`; right edges `21`, `25`, `50`, `51`. The four checked rims have radius 1.75 mm, with two on `z=0` and two on `z=8.5`; hole centers are at `y=5.5` and `y=65.5` mm. The observed x coordinate is 9.225527 mm for left and 3.725527 mm for right.
- **Candidate query:** Keep a reference to each hole-cut operation, follow the faces made by those cuts into the result, then select edges between those walls and the remaining body faces. The current model constructs the holes in a loop but does not retain named operation references; doing so is part of the proposed design.
- **Expected and checked:** Four complete circular rims were measured in each checked snapshot, each approximately 10.9956 mm long. The experimental source-and-incidence computation matched the four rims against independent geometry checks in all five tested side/height configurations.
- **Limits:** This relies on reliable operation history and a definition of which result faces came from the cutter's cylindrical side. Neither this query nor that lineage is implemented or verified here. If later operations split a wall or create new boundaries on it, all those boundaries may be returned; use the intended adjacent faces or further constraints when only the original entrance and exit rims are wanted. Assert the expected result rather than silently picking four. Geometric matching remains a fallback when construction history is unavailable, with an explicit tolerance.

```text
# Design sketch, not existing Python API.
hole_walls = faces_from(body, previously_identified_hole_source_faces)
screw_hole_rims = edges between hole_walls and the other body faces
expect 4 edges
```

The interface excludes a cylindrical seam that belongs to the same wall on both sides. The four-edge expectation matches the inspected snapshots and the experimental computation over the reported face origins; this is not a production query evaluator or a certificate of complete history. The query describes why these edges exist, without re-identifying the holes by measured radius or coordinates. Tolerances may still be needed internally for geometric comparisons; they are not the primary expression of intent.

## Bottom rims of the screw holes

- **Intent:** Refine the four-rim set to the two rims on the underside; this is an example subset, not a recorded user selection.
- **Model and stage:** The same pre-chamfer snapshots as the four-rim set.
- **Observed snapshot examples:** Two of the four measured rims are on `z=0` for each checked side and slot height. In the experimental pre-chamfer records they are left `49`, `50` and right `50`, `51`; these numbers are snapshot-scoped.
- **Candidate query:** Restrict the four-rim set to edges incident to the descendants of the selected bottom source face.
- **Expected and checked:** Two bottom rims were measured in each snapshot. The experimental source-and-incidence computation matched independent geometric checks on left 4.6 mm and right 4.7 mm; it also reported the same pairs in the other inspected configurations before the assertion was added. No production query engine was involved.
- **Limits:** A topological change could split a circular rim into arcs or alter the number of rims. A count assertion can detect some changes but cannot prove that the same entities were selected.

```text
selected = screw_hole_rims & edges_of(faces_from(body, bottom_source_face))
```
