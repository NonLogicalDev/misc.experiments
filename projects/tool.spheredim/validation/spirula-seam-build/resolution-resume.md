# Resolution change on checkpoint resume

Source audit of the pinned trainer: dataset parsing and data-manager setup precede checkpoint restore. `CamViewmats`, `CamIntrins`, and `CamDistCoeffs` are marked `Never` in `src/core/PoolSlots.h`, so they are not checkpoint payloads. Each decoded training or evaluation batch calls `set_camera_params` with the batch's width, height, model, pose, and intrinsics. The checkpoint does restore per-camera appearance parameters and optimizer buffers, so preserving the complete ordered camera identity, split, and configuration is necessary. The COLMAP parser sorts frames by its sort key; simply preserving the number of cameras does not establish the correct mapping.

The parser fits each camera to the smaller of its declared camera dimensions and the probed image dimensions. Supplying larger images with unchanged 1024×512 camera metadata therefore retains 1024×512 render dimensions. A 2048×1024 trial needs matching 2048×1024 ERP metadata and images, correctly scaled intrinsics, aligned masks, and identical camera order and poses. Do not infer that a dimension change yields correct rays without testing it.

Before a training trial, compare the entire ordered camera inventory, pose matrices, model, split, input and mask identity, and intrinsics scaling. Resume the existing 7000-step checkpoint for zero additional steps using an explicitly selected high-resolution dataset; verify the restored step, saved output dimensions, unchanged input and checkpoint hashes, and absence of checkpoint adaptation or new checkpoints. Compare high-resolution renders downsampled to the baseline dimensions at matched cameras for geometry alignment, allowing for raster sampling differences. Then, only if those checks pass and a GPU window is available, run a bounded 100-step continuation to a separate output and check finite losses, resource limits, and held-out quality against a common reference. These are proposed checks; neither a 2048 resume nor a training continuation has been validated here.
