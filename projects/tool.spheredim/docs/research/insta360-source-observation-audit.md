# Source observation audit

`scripts/audit_insv_observations.py` extracts complete decoded lens frames and complete existing equirectangular panorama frames as PNG, without perspective extraction or seam correction. The original recording remains authoritative; PNG decoding and color conversion are not the original encoded samples. It records source and image SHA-256, stream properties, decoded frame indices, exact integer presentation timestamps and time bases, timestamp differences, FFmpeg version and supplied export evidence. The closest timestamp is a container-time comparison, not proof of physical synchronization or the exact frame consumed by the exporter. The tool sorts packet PTS and checks every selected decoded frame's PTS; it fails if that indexing does not hold. A failed run may leave a partial output directory; choose a new path or inspect and remove only that partial directory.

Example, with `settings.json` containing the known settings and explicit unknowns:

```sh
python3 scripts/audit_insv_observations.py --source /path/to/recording.insv --panorama /path/to/existing-export.mp4 --output /path/outside/git/observation-audit --export-settings /path/to/settings.json --panorama-frame 0 --panorama-frame 300 --panorama-frame 900
```

For the 2026-11-15 local sample, frames 0, 300 and 900 are examples across the recording, not an identification of the operator's screenshot. The saved manifest contains the historical settings evidence and unknowns. The original export log does not establish its exact invocation, package binary, seam mode, calibration/profile or physical synchronization. Screenshot timestamp and actual source mappings remain unknown.

## Experimental single-source sample

The [separate `insta360-rs` layer](../../vendor/insta360-rs/README.md) adds an observation mode to the pinned upstream GPU path. It selects one source lens per valid pixel, bypasses gain, multi-lens blending and seam flow, and emits separate PNG validity and ownership passes after the same stabilization transform. The proposed 0.45–0.55 detail-weight crossover cut is an uncertainty margin, not measured geometry or proof that a scene region was unseen. Source bounds and calibration-mask neighborhoods are conservatively checked; true lens visibility, calibration accuracy, physical sensor synchronization, complete ray provenance and mask suitability for reconstruction remain unverified. The output is a diagnostic sample, not a validated reconstruction input.

After composing and building as documented in the layer README, copy the composed source's `src-python/python/insta360_rs/__init__.py` and the built `lib_native.dylib` (named `_native.abi3.so`) into a temporary `insta360_rs/` package directory. With that directory's parent in `PYTHONPATH`, run the following from the project root; output must not already exist and must be outside Git:

```sh
UV_CACHE_DIR=/absolute/path/to/uv-cache PYTHONPATH=/absolute/path/to/temporary-package-parent uv run --python 3.12 --with numpy --with pillow python scripts/export_observed_sample.py --source /absolute/path/to/recording.insv --output /absolute/path/to/new-output --first 900 --count 90
```

The runner requests native GPU processing, FlowState, fixed seam, 2048 × 1024 and rolling-shutter correction off. It independently runs color, validity and ownership passes, checks exported pair timestamps, validates binary masks and black invalid pixels, and hashes the original and all PNG outputs. RGB PNG sequences are canonical. It also creates a lossless RGB H.264 preview and checks its decoded pixels against the PNG frames. The preview is not the validity sidecar. Sample 900 is a representative doorway frame, not an identification of the user's screenshot. No source coordinates or actual per-pixel motion transforms are exported yet. Retain the full original recording.

The 2026-11-15 sample contains 90 frames, 3.003 seconds, beginning at paired timestamp 30.03 seconds. Both container streams' selected packet PTS advance by exactly 1001/30000 seconds, and the exporter reports paired timestamps within one microsecond of them. All three passes reported GPU execution. Binary mask and ownership checks passed for every frame, invalid pixels are black, and decoding the preview reproduced the RGB PNG pixels exactly. This establishes consistency of these outputs on this recording; it does not prove capture synchronization or exact source-ray mapping. Visual inspection of frames 900, 945 and 989 shows a narrow moving cut and changing camera heading. The cut was not measured against the reported screenshot's doorway discontinuity, so that defect is not established as resolved. The sample manifest records the exact input and output hashes and the local build identity.

## Angular margin on the sample

The original ownership crossover cut is only 1–2 raster pixels high in each column at frames 900, 945 and 989. Rough local edge extrapolations around candidate doorframe crossings gave offsets of approximately 0–16 pixels, but several fits varied by 6–9 pixels and the feature matches were not independently established. They are screening measurements, not calibrated parallax estimates. A 2° great-circle margin around the actual invalid pixels was tested on frame 900 and then applied to the 90-frame sample. This is a provisional exclusion, not a measurement of missing physical coverage.

```sh
UV_CACHE_DIR=/absolute/path/to/uv-cache uv run --python 3.12 --with numpy --with pillow --with scipy python scripts/expand_observation_margin.py --input /absolute/path/to/observation-sample --output /absolute/path/to/new-output --degrees 2
```

The tool verifies each input image hash, expands the post-stabilization invalid mask by spherical angular distance with longitude wrap, and blacks out color and ownership at excluded pixels. It checks retained pixels are unchanged and checks the decoded RGB preview against the PNG frames. An exact direct-distance regression covers wrap, poles and boundary cases. At frames 900, 945 and 989, the expanded mask spans 23–26, 23–25 and 23–32 raster rows per column respectively, excluding 2.374%, 2.348% and 2.638% of ERP raster pixels. These are raster fractions, not spherical solid-angle fractions. Visual inspection shows the discontinuities terminate at the cut; offsets on opposite sides remain. This does not fix parallax, prove correctness for other frames or identify the screenshot timestamp.

## Static calibration and playback color audit

The pinned exporter resolves this recording as X5, current embedded V6, bare housing and no lens or mounting accessory, from recorded state with sensor crop applied. The calibration canvas is 10624 × 5312; each encoded lens frame is 2880 × 2880. Lens 0 uses OmniRadtanPro `fx=4285.60`, `fy=4285.63`, center `(2655.02, 2667.75)`, `xi=2` and encoded Euler `(1.361, 0.028, 92.65)` degrees. Lens 1 uses `fx=4263.53`, `fy=4263.59`, center `(7996.07, 2650.84)`, `xi=2` and Euler `(-1.058, -0.071, 88.461)` degrees. Both identify lens ID 113. The resolver used 200° full FOV and 190° blend defaults; the blend angle was not recorded, so these values are not independent measurements. Lens 1's encoded translation is `(0.000191, -0.000054, -0.031857)`, but its units and physical accuracy are unverified. The fixed GPU projector rotates rays and uses the resolved intrinsics, but does not use that translation. Its native-to-source mapping subtracts each lens's half-canvas horizontal origin and scales by 2880/5312 in each axis. The resolved metadata is preserved beside the recording as `resolved-calibration-20261115.json`.

The source streams declare full-range BT.709 YUV. At frame 900, pixels well inside each selected-lens region differ from the previous exporter baseline by a mean absolute 1.96–2.69 RGB levels per channel (excluding dark and clipped pixels); the observation output is around two levels brighter. This is a comparison to another lossy export, not an independent color target. The original RGB H.264 preview declares RGB/full range but omits transfer and primaries. A second preview uses explicitly tagged BT.709 matrix, transfer and primaries in conventional limited-range H.264 4:2:0. Across all 90 frames and 184,059,950 valid pixels, its decoded RGB differs from canonical PNGs by mean absolute `(2.50, 2.07, 2.41)` levels, p95 `(6, 4, 6)`. Chroma subsampling and compression make some invalid boundary pixels nonblack in this display preview; the lossless PNGs and separate validity masks remain canonical. This establishes encoding behavior, not that any particular player caused the reported color difference.

Static lens alignment is being measured from separate camera-frame lens projections and support masks. A fit must be trained across multiple frames and evaluated on held-out frames before applying one fixed rotation; neither a factory calibration error nor a depth effect is established as the sole cause of the observed discontinuity.

### Fixed inter-lens alignment experiment

Nine separate full-ERP lens pairs were rendered in the camera frame, using the same embedded V6 calibration with stabilization and rolling-shutter correction off. Six frames (300, 450, 600, 750, 900, 1050) supplied feature correspondences; frames 1200, 1350 and 1500 were held out. The fitted single rotation is 2.896° and maps nominal lens-1 camera rays to lens-0 camera rays. The renderer uses its inverse on each output camera ray before applying lens 1's embedded orientation, intrinsics and sampling; it does not change the per-frame camera stabilization or use per-frame optical flow.

Across 416 held-out matches, angular disagreement decreased from median 2.944° to 0.474° and p95 3.358° to 1.948°. Each held-out frame improved on both statistics. At training frame 900 the median decreased from 3.107° to 1.680°, with substantial residual near-object mismatch. An independent rematch of actual GPU-rendered corrected images also improved at held-out frame 1350 and training frame 900; matching sets differed, so those measurements are not a paired identical-feature test. Identity rotation reproduced a probe image byte-for-byte. The fit and per-frame residuals are recorded beside the recording in `lens-alignment-probes-20261115/fit-rotation.json`.

The fit is a recording-specific calibration adjustment rather than a new factory calibration. Matching errors, different depths, physical lens-center separation and projection-model inaccuracies may all contribute to remaining disagreement; these results do not isolate their causes. The screenshot timestamp remains unknown.

### Projection-model and baseline check

An independent [Orbis X5 format investigation](https://github.com/Schabo/orbis-reframe/blob/main/docs/formats/insta360-x5.md#53-extended-calibration-strings) interprets the 13 V6 distortion slots differently from the pinned exporter's OmniRadtanPro implementation. Its proposed OpenCV-omnidir thin-prism form maps some nonzero fields differently. A numerical same-source-pixel remapping compared both hypotheses using the same 1,277 matches per lens, with independent fixed-rotation refits on the same training frames. The candidate's held-out median was 0.696° versus 0.474° for the existing projection; p95 was 1.957° versus 1.948°. It is not supported as a replacement by this sample. The comparison assumes the same lens-local coordinate basis and is not a conclusive format specification. Its direct numerical inversion converged on all tested points to better than 0.01 calibration-canvas pixel, and the calculation is in `scripts/compare_insv_projection.py`.

The same independent investigation interprets an analogous X5 lens-1 `tz` near −0.0318 as a lens separation of roughly 32 mm along lens 0's optical axis, reporting its own parallax-based sign check. Our recording's encoded vector has magnitude 0.03185762, but the units, sign and basis have not been independently verified for this recording. If its vector is in lens 0's local basis, the embedded lens-0 rotation maps it to approximately `(0.03185703, −0.00018937, −0.00004272)` in the exporter's body frame; treating it directly as a body-frame vector instead points mostly along negative Z. A physical stereo model must establish which convention applies, not assume either from the number alone. Residual match directions are being evaluated against a fixed-baseline model; depth and per-pixel source visibility remain unverified.

The pinned resolver centers the 5376-to-5312 sensor crop by subtracting 32 calibration pixels before scaling the resulting canvas to the encoded 2880-pixel frame. The independent Orbis X5 notes describe scaling principal points from 5376 while scaling focal length from 5312. With this recording's actual calibration, the two center calculations differ by at most 0.19 encoded pixel per axis: lens 0 `(1439.469, 1446.370)` versus `(1439.475, 1446.295)` and lens 1 `(1455.219, 1437.202)` versus `(1455.038, 1437.236)`. This numerical comparison does not prove either convention, but the difference alone is much smaller than the measured degree-scale mismatch.
