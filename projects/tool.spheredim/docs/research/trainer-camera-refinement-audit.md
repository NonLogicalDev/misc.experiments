# Trainer camera refinement audit

The pinned trainer's calibration correction is a per-image warp of the ground truth before the loss, not an optimization of the physical rig's camera poses. `EngineCalibWarp.cpp` describes this at its first lines; `TrainerCore.cpp` initializes one table per post-split camera when `use_calib_warp` is enabled. `TrainConfig.h` exposes `calib_correction=off|basic|accurate`: basic uses a smooth image-plane grid, while accurate adds a depth-dependent term. Defaults include a 9×9 grid, start step 1000, step 0.5, and smoothness 0.05. The prior experiments explicitly used `--calib-correction off --use-calib-warp 0`.

Direct ERP cameras use canonical intrinsics `W/(2π)` for both axes in `data/PostSplit.cpp`. The Vulkan warp samples a rectangular image: `backend/vulkan/shaders/calib_warp.slang` clamps taps to the edge and replaces out-of-image samples with the render. It does not implement periodic longitude sampling. `EngineTrainStep.cpp` applies the warp before loss and restores ground truth afterward. The default `eval_align` follows `use_calib_warp` in `TrainerCore.cpp`, so a controlled raw-pixel comparison would require explicit `--eval-align 0`.

Per-image warps do not preserve the user's requirement to use observed pixels and physical rig consistency, so they are not enabled for this work. Source searches of `TrainConfig.h`, `src/app`, and `src/engine` did not find an exposed 3D camera-pose optimization setting; this is a source audit, not proof that no lower-level camera gradients exist. Subpixel pose or calibration error can plausibly blur shared detail, but the current measurements do not establish it as the cause. Camera and rig refinement must be evaluated through physically constrained geometry and the same unaligned reference images.
